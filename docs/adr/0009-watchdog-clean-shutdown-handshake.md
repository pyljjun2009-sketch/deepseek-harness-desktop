# ADR 0009：看门狗在主进程仍存活时响应干净退出标记

## 状态

已接受并实机验证最小修复：2026-10-11 新成品通过两轮生产欢迎页正常退出、三次真实崩溃恢复，以及完整安装/替换/卸载资格。工作台原生菜单退出仍需人工验收，未据此晋升稳定通道。

## 背景与非功能要求

2026-10-10 最终候选在生产配置下两次复现：官方退出清理结束、Host 已关闭、launcher 的 `quit` 事件已经写出正确干净退出标记，但主进程与外部看门狗仍存活。无看门狗的真实桌面正常退出通过；纯 Electron 和简化看门狗对照不足以单独复现。独占生产实例完成完整快照后依然复现，排除仅由并行复制引起的超时。

诊断只停止本轮已确认干净退出的自有看门狗，没有向主进程请求终止；主进程在 265 毫秒内自行消失。原看门狗循环只检测主进程存活，在其消失之后才读取退出标记。这在该 Windows/Electron 组合下形成结束等待。

要求：正常退出不被恢复组件阻塞，也不能触发崩溃重启；保留真正异常退出时的有界恢复；不提前跳过官方任务确认、数据清理或 Host 停止；不终止其他应用，不强制退出主进程。

## 决策

在每次存活检测之前，先读取本轮独立控制文件；只有内容严格等于本轮随机 token 时，看门狗才立即正常返回。主进程消失后仍再次检查标记，保留退出竞争窗口的保护。缺失、不可读或 token 不匹配均不能当作正常退出，继续原有异常恢复逻辑。

```text
官方确认及清理完成 → quit → 写本轮 clean 标记 → 看门狗下次采样返回 → 主进程自行结束
无匹配 clean 标记 + 主进程消失 → 重试 / 禁用插件 / 已验证完整缓存
```

正常用户退出路径仍在真正 `quit` 事件写出标记，不迁移到可被取消的 `before-quit`。原有 bootstrap 受控启动故障路径也会先通知看门狗停止，再由主程序执行有界恢复与 relaunch/exit，避免双重重启；本修复不改变该故障路径，也不把它计为正常退出通过。不添加新的主进程强制退出、同名进程结束或全局守护服务。

## 取舍及备选

- 控制文件最多每两秒读取一次，额外 I/O 很小；磁盘阻塞仍可能延迟退出，不能承诺固定毫秒级关闭。
- 不在 `before-quit` 提前停止看门狗，避免用户取消退出后失去异常恢复保护。
- 不强制结束主进程，避免覆盖官方清理顺序或隐藏尚未完成的写入。
- 不仅增大测试等待时间：本次有 60 秒真实进程句柄等待失败以及停止看门狗后自行退出的因果证据。
- 控制文件/随机 token 不是对已获得同用户文件权限的攻击者的安全边界；不得把它公开在日志或 GitHub 资产中。

## 验收

增加主进程仍存活且标记已匹配、采样期间标记到达、错误 token 不抑制恢复三个回归。重新构建并密封全新载荷，不改已验证副本。新版已通过两轮生产 45 秒观察和完整快照后的欢迎页正常关闭：实际进程句柄等待、主进程及看门狗消失、七秒无重启观察、源载荷和成品哈希不变；从 clean 标记到进程退出分别约 581 和 688 毫秒，不依靠强制清理。这是本轮测量，不承诺所有环境固定退出时限，也不代替工作台原生菜单退出验收。三次真实异常退出和完整安装/替换/卸载亦重新通过，成品哈希见测试报告。旧候选的安装与崩溃通过记录仅保留为历史证据，不能代替新包资格。
